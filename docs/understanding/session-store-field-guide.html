Session Store Field Guide

What the Session Store (the sessiondb repo) does and doesn't do, written up as we read through it together. Each answer points at the file it comes from, so you can check it.

Last updated 13 Nov 2026Read from branch main @ ae974cf

Short answers

It doesn't capture
How does the Session Store capture sessions?
It doesn't watch anything. It's a passive writer: a client POSTs a raw transcript file to /v1/sessions, and the server redacts it, stores it, normalizes it to Letta trajectory-v1, and writes it to your bucket. Finding the files and deciding when to upload them is the client's job, and that client isn't in this repo. Details →
Input format only
Does it integrate with Datadog Trajectories?
Only as a file format. You can post a Trajectory session file as agent: "datadog-trajectory" and a built-in adapter converts it. Nothing talks to the Trajectory daemon or CLI, nothing reads ~/.trajectory/, and nothing sends data to Datadog. Details →
A small set
What metadata do we collect?
Owner (from the auth token), agent/source, session ID, project (any string the client sends), git branch, cwd, model, parent session, timestamps and normalizer version. There's no user email or display name, no repository visibility, no commit SHA, and no token usage. Details →
As of v0.9.0

Architecture

All the logic lives in the SDK, @dosu/sessiondb (sdks/typescript/). The server (server/src/app.ts, about 400 lines) is a thin HTTP layer on top of it: it checks tokens and calls the SDK, so the SDK is the part to read first. The SDK's connect() gives callers one API with two backends. With connect({ server, token }) the caller posts to a server. With connect({ store, owner }) the same pipeline runs on the caller's own machine and writes to the bucket directly. The bucket layout is the contract between whatever writes and whatever reads.

SDK pipelinein this repooutside this repo

How the architecture shapes what we build

Two ways to run it

  • Server mode: the laptop holds only a per-person token. Redaction can't be skipped, and the server sees transcripts before they're redacted.
  • Direct mode: the laptop holds a bucket key and runs redaction itself. Nothing goes over the network, which fits local-only tools.
  • Both write the same bucket layout, so readers can't tell which one wrote a session.

What it deliberately doesn't have

  • No database, no queue, no background jobs. The bucket is the only state.
  • No read path for consumers. Readers go to the bucket, not the server.
  • No capture. Clients find and upload sessions.
  • No push to Datadog or an OTel collector, even though OTLP objects could be posted to one as-is.
Question

Server configuration

The server is configured only through environment variables. There's no config file, no flags, and no admin API. Bun reads .env from the working directory, and compose.yaml passes the same file to the container. .env.example is the template. Everything is read once at startup in server/src/main.ts, so any change needs a restart.

What happens at startup

The server checks every setting and exits with a one-line error if one is wrong. It then writes the layout marker and a probe object for each listed owner, so wrong bucket keys fail at startup rather than on the first upload. The startup log line names the format, the store URL and the owners.

No per-owner or per-team settings. To give teams different redaction rules, formats or buckets, you run one container per team. Tokens are fixed at startup, so adding or rotating one means a restart (signed JWTs avoid this).

Question

Storage: no database

sessiondb doesn't use Postgres, SQLite or any other database. The server depends only on the SDK, and the SDK depends only on @letta-ai/trajectory. The object store (S3, R2, or a folder via file://) holds all of its state. docs/server.md says there is "no database, no volume, no background work, and no state outside the bucket", so any number of server instances can run, including zero.

Usually a database jobHow sessiondb does it
A sessions tableOne metadata.json per session at owners/<owner>/sessions/<archive_id>/
Rows of contentWrite-once objects: raw.N.*.gz and trace.<hash>.json.gz
Primary keyarchive_id = sha256(owner, agent, session_id)
Change log / replicationowners/<owner>/changes/<stamp>-<hash>.json, which readers follow with a cursor
Avoiding conflicting writescontent_hash makes repeated writes harmless, and each write is verified by its ETag or by reading it back. There are no real transactions.
QueriesListing objects by prefix only. There's no index, so you can't search by branch, project or text.

What this costs: there's no search beyond listing by owner. The change feed's order depends on laptop clocks, so readers need a lag window. Updating metadata.json means reading the object, changing it and writing it back, and the offset check is the only protection against two uploads of the same session at once.

A hint of Postgres downstream. trace/canonical.ts:26 strips NUL characters because "Postgres text and jsonb reject NUL". So at least one reader, probably Dosu's backend, loads traces into Postgres. Databases sit beside the bucket as derived copies, which is the same pattern the ClickHouse plan uses. (Which reader this is hasn't been confirmed.)

Question

User auth

Every request carries a bearer token, the token names one owner, and the request can touch only owners/<owner>/. There are no logins, passwords, sessions, roles or user records. The code is in server/src/app.ts (authorize) and server/src/signed-token.ts.

Token kindHow it's checkedSuits
Listed token (SESSIONDB_TOKENS / SESSIONDB_TOKEN)A timing-safe comparison against each entry; a match gives that entry's name as the owner. Tokens must be 16+ characters, duplicates are refused, and changes need a restart.A self-hosted team
Signed token (SESSIONDB_TOKEN_SECRET)An HS256 JWT: anything other than HS256 is refused, the signature is checked with a timing-safe compare, exp is required and must be in the future, and sub must be a valid owner nameThe hosted setup: the Dosu backend mints one per user, and the server never sees a user list

For each request

The server reads Authorization: Bearer <token>. A missing, wrong or expired token gets 401 unauthorized, with no reason given. The owner the token names selects a client scoped to that owner's folder, and every route goes through it: upload, list, read, trace, delete, and /v1/changes. /healthz is the only route that needs no token, and GET /v1/me tells a client which owner and bucket it maps to.

Consequences

  • The token is the identity. The server doesn't check email, org or team. Whoever mints tokens decides who someone is.
  • No sharing between users. No owner can read another's sessions through the API, and there are no team-wide reads. Each team needs its own container.
  • Signed tokens can't be revoked. A leaked JWT works until its exp. Short expiry is the only protection, and rotating the secret cuts off everyone at once.
  • Renaming an owner moves their data. The old folder stays in the bucket and the new name can't see it.

Bucket keys skip auth entirely. Readers such as Dosu's backend, or a future ClickHouse indexer, read the bucket with their own keys and see every owner. Token auth protects only the HTTP API.

Question 1

How sessions get in

The Session Store is push-based. Coding agents (Claude Code, Codex, Cursor and others) already write a log file on the developer's machine. Something on that machine reads the file and POSTs it. The server never reaches out to a laptop, and it has no hooks or file watchers. The README states the repo's scope directly: the server "takes a log over HTTP".

What happens to an upload

  1. Store raw, redacted. The native log is scrubbed in three passes: whole tool results that touched secrets files or ran secret-printing commands, your own patterns, then built-in token and credential patterns plus an entropy check. It's written as raw.N. Redaction can't be switched off. sdks/typescript/src/redact/
  2. Normalize. The stored raw (not the bytes that came over the wire) is converted to Letta trajectory-v1 records with @letta-ai/trajectory, plus fixups for each source. Because it works from what's stored, any session can be re-normalized later. sdks/typescript/src/normalize/index.ts
  3. Decide. If there's under 2,000 characters of conversation, no user turn, or no reply, the session is trivial: the raw part is kept but no trace is written. If the session was uploaded before, only the new tail is written as a continuation. ingest/worthiness.ts, ingest/session.ts
  4. Publish. content_hash covers what was said, not timestamps, so re-sending the same conversation writes nothing. The steps are: write the trace, verify it (ETag or read-back), update metadata.json, then append to changes/. store/publish.ts, spec/layout.md

Accepted formats (agent values)

agentConverted byChunkable
claude-code, codex, cursor, pi, gemini-cliLetta adapters + fixupsYes (JSONL)

Clients can send a whole log or append chunks. A chunk's offset must equal the last bytes_total, otherwise the server returns 409. The server keeps the hash state between chunks, so a long session costs only what was appended.

Who is the uploader? No uploader exists in this repo. According to Dosu team knowledge, the Dosu CLI fills that role (its beta "shipper" path, dosu-cli PR #259), and the Dosu backend mints a signed per-user token for each person (SESSIONDB_TOKEN_SECRET). If we want to change when or which sessions are captured, that work happens in the CLI, not here.

Question 2

Datadog Trajectory

Trajectory is Datadog's capture daemon for coding agents. It writes one file per session at ~/.trajectory/trajectories/sessions/<date>/session-<id>.jsonl, with one event per line. sessiondb can read that file format, and that is the whole integration.

What exists

  • An adapter: normalize/datadog-trajectory.ts
  • Accepted as agent: "datadog-trajectory", whole or chunked
  • Trace source is set to datadog-trajectory:<client>, e.g. …:claude-code
  • Handles backfilled sessions (trajectory session import)
  • Golden fixtures: datadog-claude-session, datadog-backfilled-session

What doesn't

  • Nothing reads ~/.trajectory/ or runs the daemon
  • No export to Datadog (OTLP traces can go to any collector, but nothing sends them)
  • The same session sent natively and via Trajectory becomes two separate archives, and nothing links them

What if the data is already in Datadog?

It doesn't work today. sessiondb reads only the local file the daemon writes on each laptop. Trajectory also publishes to Datadog itself, as LLM Observability traces plus metrics (it uses DD_API_KEY). Those traces are a different shape from the local file:

  • each turn is a separate trace
  • agent messages, tool calls, real LLM calls and synthetic "turn usage" carriers are spans
  • sessions are linked by a correlation tag, trajectory.trace_correlation.session_id

Trajectory's own docs (docs/LLM-OBS-SPAN-TAGS.md) describe this. Nothing in sessiondb can read it: there's no Datadog API client, no DD_* configuration, and no adapter for LLM Observability spans.

To ingest from Datadog we'd needNotes
A pullerDatadog's LLM Observability export is pull-only. It's a REST API to list and search spans (/api/v2/llm-obs/v1/spans/events[/search]), still in preview, that needs the customer's API and app keys and returns cursor-paged results filtered by @session_id:. I found no push option for spans: log forwarding to custom destinations covers logs only, and webhooks send monitor alerts, not data. So it means polling, and per sessiondb's design the poller belongs in a client, not the server, which has no background jobs.
A new adapterConverting spans to trajectory-v1: put the turn traces back together into one session through the correlation tag, order the spans, and drop the synthetic spans. It's a different adapter from the one for the local file.
Enough content capturedAt Trajectory's minimal capture level, no prompt or output text is sent to Datadog, so every session would come out trivial. standard/full include content, but assistant text can be cut off at a byte limit.

The simpler path is to read the local file on the same machine where the daemon runs, alongside its Datadog publishing. That's what sessiondb already supports. One upside of pulling from Datadog: its spans carry token usage, which is the data the file adapter drops. I haven't checked whether Datadog's API returns full span content in bulk, or whether the daemon keeps local files after it publishes.

The docs and the code disagree. docs/server.md says session_id and parent_session_id "come from the file's session_start". In the code, the adapter only checks that session_start.session_id exists. The archive ID is built from the session_id in the request body, and parent_session_id also comes only from the body (server/src/app.ts:295). A client that leaves these out loses lineage, and if its session_id differs from the file's, nothing catches the mismatch.

Follow-up questions

Why things get dropped

Read this first: "dropped" means left out of the trace (the normalized copy). It never means deleted from the archive. Every upload is first stored as a redacted raw part (raw.N.jsonl.gz), and traces are always rebuilt from that stored raw. A trivial session and a Trajectory file's llm_call events both stay in the bucket, and a later normalizer can turn them into a trace.

Why are trivial sessions skipped?

The code says why: under 2,000 characters is "a greeting rather than an investigation" (sdks/typescript/src/ingest/worthiness.ts). A session is trivial if any of these is true:

  • it has no user record
  • nothing answers it (no assistant or tool record)
  • its text plus tool arguments plus tool results add up to under 2,000 characters

The check counts size rather than turns on purpose, so a terse agent run that's mostly tool calls still counts. A trivial session keeps its raw part. It gets no trace and no head, and it never appears in changes/.

The commits and docs don't say why the threshold is 2,000. Two things suggest where it comes from:

  • The main reader learns from sessions. The change feed is what Dosu's backend reads to extract knowledge. Every published trace is something a reader fetches and processes, and "hi" / "thanks" sessions would only add noise and cost.
  • The number came from the Dosu CLI. The CLI's isWorthStudying uses the same 2,000 characters but counts differently: it needs about 4 turns and counts only user and assistant text, not tool calls (per Dosu team notes). The server's rule is more lenient. A session can pass the server and still be skipped by the CLI before it's ever uploaded.

A session in chunks is judged once. Until it has a trace, each new chunk re-checks the whole log so far. After that, every chunk with records in it ships, even one that's all tool traffic (commit 8acb777).

Known bug: tails can be lost. A whole re-upload that sends shipped judges only the new tail on its own (isTrivialTrajectory(plan.fresh), ingest/session.ts:265). A tail under 2,000 characters, or one with no user turn, comes back trivial. The response still includes the whole session's records_total and prefix_sha256, and the docs tell clients to save those. The next upload then starts after records that were never written to a trace. Chunked uploads don't have this problem. It's described in the Dosu note "SessionDB Trivial-Tail Data Loss", and it's still in the code at v0.9.0. The layout spec says a tail "is judged as part of the session", which matches the chunk path but not the whole-upload path.

Why does the Datadog adapter drop llm_call, turn_end and the session_start extras?

The adapter's own comment gives the stated reason: these events "carry no conversation". The actual constraint is the target format.

DroppedWhy
llm_call (tokens, cost)Letta trajectory-v1 has no field for usage. Records are only meta, user, assistant, tool, reasoning, observation and system, and validateRecords removes any field it doesn't know. That's also why OTLP spans don't include gen_ai.usage.*. No other format sessiondb accepts has usage data either.
turn_endA turn boundary. Turns are already implied by the order of user and assistant records, so it adds nothing to a trace.
subagent_start/stopThey repeat what the Agent tool's result already says. The subagent's own session arrives as its own file.
inventory.snapshot, permissionsState and lifecycle events with no matching record type.
client_version, provider, start_triggerThe meta record has only source, cwd, git_branch and model. Adding a field means changing the format, which belongs to @letta-ai/trajectory, not to us.
parent_session_idNot a format limit. Traces already have metadata.parent_session_id, but the adapter has no way to pass it there. Only the request body sets it. This looks like a gap, not a design choice.

The trajectory-v1 format also protects deduplication: content_hash covers only what was said, so extra telemetry fields wouldn't change the hash anyway. The adapter landed in 72c7e35 (29 Oct). The same day, 5880a23 removed an earlier bucket scanner and made Trajectory "an input format only". That scanner needed an always-on server and bucket credentials on every laptop, and it left unredacted files in the bucket.

If we want token usage, there are three places it could go:

  1. trace metadata, outside the records, the same way parent_session_id and normalizer are stored
  2. new gen_ai.usage.* attributes on the OTLP spans
  3. upstream in trajectory-v1

Because the raw parts are kept, any of these could be backfilled for sessions we already have.

Design sketch · not built

ClickHouse search

Recommendation: add ClickHouse as a search index built from the bucket, not as a replacement for the bucket. The architecture is already shaped for this. Readers tail changes/ with their own key, every trace already has a list of events that's easy to search (role, text, tool name, ok), and every trace can be rebuilt from the stored raw. An indexer is just one more reader, so the write path, redaction and the three core guarantees stay as they are. If the index breaks, you rebuild it from the bucket.

Changes required

AreaWhat changesSize
1 · Indexer new
  • A long-running reader built on the SDK's readChanges / getTrace.
  • The feed is per owner (owners/<owner>/changes/), so the indexer lists owners/ to find owners and keeps a cursor for each.
  • Change stamps come from laptop clocks, so it re-reads a time window behind each cursor and drops entries it already has, by key.
  • Reads metadata.json for session fields and trace order, and converts traces with fromOtlp in otlp buckets.
  • Fills the index for existing sessions with a one-time scan of sessions/.
M
2 · Schema new
  • sessions: a ReplacingMergeTree keyed by owner and archive_id, newest updated_at wins. Holds agent, source, project, branch, model, cwd, parent, times, head and status.
  • events: a MergeTree ordered by owner, archive_id, trace position and index. Holds role, text, tool_name, ok and timestamp, with a full-text or n-gram index on text.
  • Optionally an embedding column with a vector index, for semantic search.
S
3 · Search API + access new
  • Today the only access rule is "a token sees its own owner folder". Search for one owner is easy.
  • Search across a team needs team, org and visibility fields, which aren't collected, so this is the real design decision.
  • Put it in a separate service, or behind an optional server route, so the server stays stateless by default.
M–L
4 · Session-wide event order change
  • events[].index starts at 0 in every trace object, so a session sent in chunks has several overlapping index ranges.
  • The indexer has to compute each event's position from the order of traces in metadata.json, or each trace could record its starting event offset (a small layout addition).
S
5 · Better filters changeSearch filters are only as good as the metadata. project is free text, there's no org or visibility field, and there's no token usage. Normalizing the repository to a canonical remote is the first fix to make.S–M
6 · Deletes, redaction, reindexing change

  • Index only redacted traces, never raw parts.

S
7 · Operations new
  • A ClickHouse deployment (Cloud or self-hosted), schema migrations, and monitoring of how far the indexer lags behind the feed.

Alternatives I'd avoid

ClickHouse as the store

  • Breaks "readers need only a bucket key" and the documented layout.
  • Loses the raw parts and the immutable trace objects.
  • Ties the archive to one database rather than an open format.

Writing to ClickHouse from the server

  • Adds a database to a server that today has none.
  • Ties upload success to ClickHouse being up.
  • Misses direct-mode SDK writers, which never go through the server.

Questions that shape the build

  • What kind of search? Keyword (a text index), semantic (embeddings plus a vector index, and an embedding step in the indexer), or analytics such as tools used or failure rates (plain columns are enough).
  • Semantic search in ClickHouse: exact search works anywhere, using cosineDistance / L2Distance over an Array(Float32) column. Approximate search uses the vector_similarity index (HNSW via usearch), available from 25.8. ClickHouse doesn't create embeddings, so the indexer must call an embedding model. HNSW keeps the whole index in memory and rebuilds it when data parts merge. Every query is also filtered by owner, so filtered vector search needs testing.
  • Who searches? Individuals over their own sessions, a team, or Dosu's backend and agents. This decides item 3.
  • How fresh? The feed's clock skew means a few minutes of delay is normal. Anything closer to real time needs a different trigger.
