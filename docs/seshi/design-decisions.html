Seshi design decisions

Seshi turns sessiondb from an upload-only session store into a toolkit for the whole session lifecycle: capture, ingest from other systems, redact, store, and search. This page records each decision we need to make, the options, a recommendation, and what is still open.

Every decision has an ID (X5.2, F4.3) so we can refer to it in discussion. Recommendations are proposals until we agree on them.

Decide these first

Most feature decisions depend on these four. Settling them first avoids redoing feature work.

  1. Tenancy (X1). One deployment per organization makes OTLP tokens, connector keys and owner mapping simple. Multi-tenant changes the layout and every auth check.
  2. Identity model (X5). Three of the ten features ingest org-level data whose user identity is only a claim. We need one rule for who a session belongs to.
  3. Stored format (X6.2). Today a bucket is locked to letta or otlp by its first writer. OTLP ingestion and search both depend on what we store.
  4. Background work (X7). The server has no background jobs today. Three pollers, span assembly and the search indexer all need them.

X1Tenancy

Who one seshi deployment serves, and where the walls between organizations sit. Sharing inside an org (teams, who can read whose sessions) is an access question and belongs in X5.

The real dividing line is whether configuration is a file or data. With one org per deployment, config stays a file plus env (F1) and a restart applies it. With many orgs per deployment, adding a customer cannot require a restart, so config, connector secrets and IdP settings become data managed over an admin API, and seshi needs somewhere to keep them.

X1.1Agreed

One deployment serves one organization

Options
  • Single-tenant: one org per deployment; owners are people and services inside it.
  • Multi-tenant: orgs/<org>/owners/<owner>, org on every token and check.
Recommendation
Single-tenant. A host that serves many orgs runs one instance per org (X1.2).
Why
Every external credential in scope is already org-level: Claude Console destinations, Datadog API and app keys, Cursor service accounts, S3 source buckets. Owner mapping, redaction rules and search permissions are also per org. Multi-tenancy would add an org check to every path and turn config into data, for a case a hosting layer can solve.
X1.2Agreed

Build so one process can later host many isolated instances

Detail
No module-level singletons. Config, store, auth, workers and the search index hang off an Instance built from one config. A later mode such as seshi serve --instances /etc/seshi/orgs/*.toml can then run many orgs in one process, each with its own bucket, keys, IdP and workers, routed by hostname.
Why
Testability first: each test builds its own Instance with its own config and store, so tests run in parallel without shared global state. It also leaves room to remove the "N idle processes" cost of single-tenancy later, without putting org checks into the data model.
X1.3Agreed

Each org's data sits behind its own keys

Detail
One bucket per org, or one prefix per org with bucket keys limited to that prefix by IAM policy. Never one set of keys that can read several orgs.
X1.4Agreed

A deployment refuses another deployment's data and tokens

Detail
The layout marker records a deployment_id and org; the server will not start if its config names a different org. The OIDC audience is specific to the deployment. Seshi tokens are stored as hashes in the deployment's own bucket, so they are not valid anywhere else.
Why
Catches the easy mistakes: a config pointed at the wrong bucket, or a token copied between environments.
Priority
Low. It guards an edge case, so keep it to the marker check and the audience setting; nothing more elaborate.
X1.5Agreed

No migration of shared deployments

Decision
Assume no hosted multi-org sessiondb deployments exist today. Seshi ships no tool to split a shared bucket by org.
Note
The o-<org>.u-<user> owner naming seen earlier is treated as not in use. If a shared deployment does turn up, its owner names start with the org, so splitting it by prefix stays possible.

X2Runtime and distribution

X2.1Agreed

Stay on TypeScript and Bun

Options
  • TypeScript on Bun throughout (today's stack).
  • Go for the CLI and hooks, TypeScript for the server.
  • Rust or Go for everything.
Recommendation
TypeScript on Bun for everything, so normalizers and redaction run identically on the client and the server.
Why
Client-side pre-redaction (F2.4) and local normalization need the same code as the server. A second language means two implementations of every adapter and rule engine.
X2.2Agreed

One seshi binary for CLI, hooks and server

Options
  • One binary built with bun build --compile; seshi serve runs the server.
  • Separate seshi (client) and seshi-server binaries.
Recommendation
One binary, plus a server Docker image built from it.
Revisit if
Binary size or the cold start of seshi hook (which runs on every agent turn) becomes a problem. Fallbacks, in order: a tiny shell shim that appends to the spool for hooks, then a separate server binary.

X3Repository structure

Today: sdks/typescript holds normalize, redact, store, trace and ingest in one published package (@dosu/sessiondb); server/ is one HTTP file, an entry point and token code; spec/ holds the layout, OpenAPI and test data.

Because X2.2 puts the CLI, hooks and server in one binary, package boundaries no longer decide what ships: everything is in the binary. They now do two jobs: keep layers apart so each can be tested alone (X1.2), and let each command load only the code it needs, so hooks start quickly (X3.3). Packages are grouped in a folder per language (X3.9), and everything specific to one vendor or agent lives in integrations/ (X3.11).

X3.10Agreed

How non-TypeScript packages fit

Scope
Other languages get clients for the HTTP API and read-only readers of the bucket layout (for a service that reads the bucket directly). The pipeline, redaction and agent adapters stay TypeScript-only and run in the binary, so they are never ported. A tool in another language that needs redaction or normalization calls the binary (for example seshi redact --stdin).
Contract
Anything another language reads is defined in spec/ first: OpenAPI for the API, JSON Schema for stored objects (metadata, trace, change entry) and the envelope, and the canonical text and hashing rules in prose. Each language generates its types from those files; ts/model is generated too, and CI fails if a generated file is stale. Types only the binary reads, such as config, stay code-first and emit a schema for editors.
Conformance
spec/testdata holds inputs with expected outputs: stored objects to parse, content hashes and archive IDs to reproduce, API exchanges to replay. Every language's package runs the same fixtures. Today's canonical text already follows Python string rules so other languages can reproduce hashes (trace/canonical.ts).
Tooling
Each language package keeps its own toolchain file (pyproject.toml, go.mod) and releases on its own: npm, PyPI, and Go tags such as packages/go/client/v1.2.0. CI runs a job per language, filtered by path, and every job runs on changes to spec/.

By vendor. Each integration exports one object that lists what it provides: format adapters, hook handlers, sweep paths, connectors, installers. apps/seshi imports every integration into a static registry and passes it to the Instance and to ts/capture.

X4One ingest pipeline

Five ways in, one way through. Every source produces an envelope, and every envelope goes through the same stages. Today's pipeline stores the redacted raw first and then builds the trace from what was stored (ingest/session.ts). Seshi decides everything in memory and writes once at the end. It stores only the normalized, redacted trace, never the raw payload (X6.3), so nothing is written before regex redaction, the session filter and model review have run.

X4.1Agreed

A versioned envelope is the only input to the pipeline

Fields
source (upload, hook, otlp, datadog, s3, cursor-cloud), source_id, format, session_key, payload (bytes with offset, or a span batch), caller (the verified principal and credential ID), claims (identity the data asserts: email, account IDs, git email), owner (resolved by X5.4), idempotency_key (X4.7), provenance (object key, ETag, API cursor).
Where
The schema is in spec/ and the type is generated into packages/ts/model (X3.10). The HTTP routes build envelopes from requests; integrations build them through the submit() context from packages/ts/kit (X3.11).
X4.2Agreed

Two payload shapes: append-only logs and span sets

Detail
Transcripts (Claude Code, Codex, Cursor local, Trajectory files, S3 objects) grow by appending, so the existing offset and continuation protocol applies. Spans (OTLP, Datadog) arrive out of order and repeat, so they go to a span assembler that collects them per session and rebuilds the whole trace (F4.4). Cursor Cloud runs append to their agent's session and use the log path.
X4.3Agreed

Decide in memory, write last

Stages
  • Authorize the caller and resolve the owner.
  • Normalize the payload in memory (with the session's earlier stored parts when it is a chunk).
  • Apply regex redaction to the normalized records: text patterns to every string field, sensitive-file and secret-command rules to tool calls (F2).
  • Apply the session filter (X4.10).
  • If a review policy applies, the decision model labels the envelope allow, redact or drop, and for redact a small LLM finds the text to remove (F3).
  • Write the trace, the head and the change entry. The raw payload is discarded.
Why redaction comes before anything is written
Unredacted data is never stored. With no raw (X6.3), the trace is the only thing written, so the rules run on the normalized records, where tool calls, file paths and outputs are already separate fields. Today's code runs the rules over the raw transcript and then the built-in patterns again over the records (normalize/index.ts), because it stores both.
Change from today
Today raw is written before normalizing, so a normalize failure still leaves something to rebuild from. In seshi a session that fails to normalize stores nothing. A failure record keeps its provenance (X4.8), and the source supplies it again once the adapter is fixed: the transcript is still on the laptop, the object still in S3, the spans still in Datadog.
X4.4Agreed

Logs are processed inline; spans, review and indexing are async

Detail
  • Logs (uploads, hook chunks, poller submissions): processed through publish before the call returns, as today, so an uploader learns at once about 409 offset_mismatch (with expected) or 422.
  • Spans: the OTLP call returns once the batch is in the span store, so senders are not held up; the assembler publishes later.
  • Model review: inline, before anything is written. Uploads come from the background uploader or a poller, so the extra seconds hold up no developer. If the provider fails, the server retries, then the policy's on_failure setting decides: skip review or drop the envelope (F3.4).
  • Search indexing: a background job (X7).
Rejected
A durable inbox for everything. It would turn every upload error into a later failure record and break the continuation protocol, which needs an immediate answer.
X4.5Agreed

The same session arriving by two routes

Today
archive_id = sha256(owner, agent, session_id). Each source fills these differently: a Claude Code hook sends the agent's session ID; OTLP uses anthropic.session.id; Datadog uses trajectory.trace_correlation.session_id; Cursor Cloud uses the agent ID.
Problem
One Trajectory session can arrive from the local daemon file (verified owner, datadog-trajectory log) and from the Datadog poller (claimed owner, spans). Different owners or agents give different archive IDs, so it is stored twice.
Options
  • Accept duplicates; record origin_agent and native_session_id on both so search and readers can collapse them.
  • Source precedence: an operator names which route wins per agent, and the pipeline skips a session whose native ID the winning route already holds (needs a small lookup object per native ID).
  • Refuse configurations where two routes cover the same agent.
Decision
Accept duplicates for now. Record origin_agent and native_session_id on every session so search and readers can collapse them. Add source precedence later if duplicates turn out to matter.
X4.6Agreed

When a write replaces a session instead of extending it

Today
Checked in the code: a whole upload (offset 0) for an existing session deletes the earlier raw parts and resets the chunk state (putRaw with whole). If the new records do not extend what was shipped, the pipeline publishes a full new head instead of a continuation. So any token that can write for an owner, and knows a session ID, can replace that session's content. Earlier trace objects stay listed.
Options
  • Keep silent replacement.
  • Reject a whole upload that does not extend the session with 409 conflict, and require an explicit replace flag that only the original writer or an admin may use.
Decision
Explicit replace. A whole upload that does not extend the session gets 409 conflict unless it sets replace, which only the session's original writer or an admin may use. Document formats that cannot be chunked (ATIF, OpenCode exports) are rewritten whole by design, and their original writer can still replace. The same rule settles F6.3.
X4.7Agreed

Every envelope carries an idempotency key

Keys
Hook or upload: session and byte offset. S3: bucket, key and ETag. OTLP and Datadog: trace and span IDs. Cursor Cloud: agent ID and run ID.
Why
A poller submits and then saves its checkpoint; a crash in between makes it submit again. With idempotent stages that is harmless, so delivery is at-least-once and the result is the same as once.
X4.8Agreed

Failures with no caller to tell

Detail
Pollers and the span assembler have nobody to return a 422 to. A permanent failure (unknown format, over a size limit, adapter error) writes a failure record under sources/<id>/failed/ (X6.4) with provenance, code and message, never content, and counts toward source health. A transient failure (store or network) retries with backoff and does not move the checkpoint. seshi sync failed <id> lists them.
X4.9Agreed

Rebuild by re-ingesting from the source

Detail
With no raw stored, seshi reprocess asks the source again: the uploader resends laptop transcripts, and pollers rewind their checkpoint for S3, Datadog or Cursor. It is filtered by source, agent, normalizer version or date, and writes new heads and change entries. Metadata already records the normalizer version, which picks the sessions to redo.
Limit
It works only while the source still has the data (X6.3). Older sessions keep their current trace.
Revised 15 Nov 2026
The server keeps no raw logs, so seshi reprocess cannot rebuild sessions uploaded from laptops. Instead the server marks a session stale when it was built by an older normalizer, and the uploader resends stale sessions whole with a new rebuild envelope field, which makes the server build and review the session again even when the log only extends what is stored. seshi capture resend [--all | --session <id>] does the same by hand.
X4.10Agreed

The session filter, configurable

Rename
Today's "worthiness" check (isTrivialTrajectory) becomes the session filter, and its outcome trivial becomes filtered.
Rules
Today's rules, hard-coded, become config under [filter] with today's values as defaults, and each source can override them:
  • min_chars = 2000: text, tool arguments and tool results, excluding the meta record.
  • require_user = true: at least one user record.
  • require_reply = true: at least one assistant or tool record.
enabled = false keeps every session.
Outcome
A filtered session is not stored. It is counted in source health, which makes a misconfigured source visible (Datadog minimal capture, metadata-only OTLP).

X5Identity and access

Today a static token or an HS256 JWT names the owner, and that token can do everything for that owner. Anyone holding the shared HS256 secret can mint a token for any owner, and nothing can be revoked without a restart. Seshi needs known people, scoped and revocable tokens, and a rule for org-level sources.

An identity provider (IdP) is optional, including in production (X5.12). Without one, the org trusts its members: everyone holds an org key and says who they are, as Datadog Trajectory does. With one, people sign in and their identity is verified. Both modes share the same people records, owner IDs, tokens and scopes. One org per deployment (X1.1) means at most one IdP. Uploads come from a background uploader (F9), so the upload credential must work for months without a person present.

Revised 15 Nov 2026

F9Capture integrations

Hooks in each coding agent capture sessions as they happen, a sweep catches what hooks miss, and a status indicator tells the developer whether this session is being captured. Capture can be turned off for everything, a repo, a folder, or one session.

F9.1Agreed

Hooks write to a spool and exit

Detail

It always exits 0 and never blocks the agent; errors go to a log. A background uploader drains the spool and sends only the new bytes with the continuation protocol.
Uploader
Started on demand: the hook starts it if it is not running, and it exits after a few idle minutes. This works the same on macOS, Linux and Windows with nothing to install. seshi capture install --service adds a launchd, systemd or Task Scheduler entry for people who want uploads to continue between agent sessions.
Whole log first
Until a session has a trace on the server, the server stores nothing for it and accepts only the whole log (X6.3). On 409 with expected: 0, which today's protocol already returns, the uploader resends from the start.
Paths
Spool and state live in ~/.local/state/seshi/ on macOS and Linux and %LOCALAPPDATA%\seshi\ on Windows. Hook commands work in sh, PowerShell and cmd (F8.4).
Revised 15 Nov 2026
The uploader stays running while uploads or retractions are waiting to retry, for at most 30 minutes after its last success, then exits as before. A pass whose work all failed no longer counts as idle.

  • Claude desktop app (Code tab), which has no status line: a mod with a clickable Session Capture ◉/⏸ chip in the footer, as in the Session Capture prototype (dosu-ai/dosu PR 13997). Clicking it sets the session toggle below.
  • Cursor and Codex: seshi capture status and a first-run notice.
F9.5Agreed

Capture rules at four levels, toggleable inside a session

Levels
  • Global: on or off for this user, in the CLI config. On by default once capture is installed.
  • Repo: .seshi/config.toml at the repo root, committed, so it applies to everyone who works in the repo (capture = false).
  • Directory or workspace: personal path rules in the CLI config, matched by path prefix, so they cover folders that are not repos and are never committed:
    [[capture.paths]] path = "~/clients/acme" capture = false
  • Session: on or off for one agent session, keyed by agent and session ID.
How they combine
Shared rules can only turn capture off: an org rule (such as "only repos whose remote is in our GitHub org", delivered with the CLI config) or a repo's capture = false always wins. Otherwise the most specific personal level that says anything decides: session, then directory (longest matching path), then global. So a session can be turned on in a folder that is off, but not in a repo the team has excluded.
Toggling in a session
  • A /seshi skill in the Claude Code plugin: /seshi capture off, on, status. It runs seshi capture off --session <id>, which writes the session's entry in the local state file. To check: how the skill gets the current session ID (an environment variable or substitution in the skill).
  • The desktop mod's chip and /session-capture command (F9.4) write the same entry.
  • Elsewhere: seshi capture off --session <id>, or seshi capture pause 2h for everything.
Turning off mid-session
Nothing more of the session is uploaded, by hooks or the sweep, and what was already uploaded is retracted (F9.7). Sessions under the session filter's size (X4.10) were never stored, so turning off early usually leaves nothing to retract.
Where the state lives
One local state file per machine, read by hooks, the sweep, the status line and the mod. This answers the prototype's open question of where the flag should live so capture can read it.
Revised 15 Nov 2026
seshi capture pause stops sessions where they are. A session running when the pause starts keeps what it has uploaded and uploads nothing more, ever; a session started during the pause is off. Nothing is retracted, and a whole-log resend (after a 409, a moved transcript or a replace) sends only up to the offset where the session stopped. Sessions started after the pause ends are captured as usual.
F9.6Agreed

Detail

F9.7Agreed

Turning a session off retracts what was uploaded

Problem
The uploader's credentials cannot delete: the device token is write-only (X5.2) and the org key cannot delete at all (X5.3).
Decision
A retraction secret per session. On a session's first upload the uploader generates a random secret, keeps it in the local state file next to the session's toggle, and sends only its hash, which the server stores in the session's metadata (retract_hash). Turning the session off makes the uploader stop and send DELETE /v1/sessions/{id} with its normal credential and the secret. The server checks it against the hash and runs the normal delete: a tombstone in the change feed, trace objects removed, the session dropped from search.
Why
It works the same with or without an IdP and does not depend on the claimed username. Only the machine that uploaded a session can retract it; a leaked org key or device token cannot delete anyone else's sessions, because the secret never leaves that machine. Nobody has to sign in again mid-session.
Details
  • The change entry records reason retracted, never the content, so admins can see it happened.
  • An upload in flight when the session is turned off finishes first, then the retraction runs. If the uploader is not running, the retraction waits in the spool.
  • Turning the session back on uploads it from the start as a new session; the replace rule (X4.6) does not apply because the old one is gone.
  • If the state file is lost (reinstall, new machine), the secret is gone and deleting falls back to seshi sessions rm with an IdP, or an admin.
  • Server setting capture.allow_retract, on by default, for orgs that do not want developers deleting sessions after the fact.
Options considered
Let the credential that wrote a session delete it (the org key is shared, so any member could delete any key-uploaded session); require a fresh sign-in to turn off (friction, and impossible without an IdP); delay a session's first upload (useful alongside, not instead).

Access

  • With an IdP: a write-only device token; the owner is the person it was issued to (X5.7).
  • Without one: the org key plus the resolved username, recorded as owner_basis: claimed (X5.12).
  • Agent account IDs and git email are sent as claims, for spotting mismatches.

Data and storage

  • Spool entries hold paths and offsets, not copies of transcripts.
  • Optional client-side redaction (F2.4) runs in the uploader.
  • Capture rules, session toggles and retraction secrets stay on the machine; the server sees only what was uploaded and a hash per session.

Mint for success and the brand mark, lilac for search results and links, spark for warnings and work in progress; red stays the terminal's own for errors. Seshi never sets the terminal background. Truecolor when COLORTERM says so, the nearest 256-colour value otherwise, then the basic 16.
Light terminals
Deep teal replaces mint, as v1.1 requires. Until lilac and spark get light variants (B1.7), search and warnings fall back to the terminal's own magenta and yellow, which the user's theme already tunes for its background. Seshi detects the background from COLORFGBG or an OSC 11 query with a short timeout, defaults to dark, and SESHI_THEME=light|dark overrides it.
Never colour alone
Every coloured status also carries a word or symbol (v1.1 rule), so output reads the same with colour off.
Off switches
No colour or glyphs when output is not a terminal, when NO_COLOR is set, with --no-color, and always with --json (F8.1). Status line output stays one short line.
Tone
"Quietly playful, clearly technical": short success lines may carry the state word ("Collected 3 sessions"); everything else is plain.

Decision

Problems

It says what the indicator does, to people who have not heard of seshi, and it matches the desktop chip so both surfaces read the same.
